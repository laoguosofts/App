## ✨ microG 是什么

microG 是一套开源的谷歌移动服务（GMS）兼容层，它把安卓设备上依赖谷歌框架才能运行的应用——聊天、支付、地图、推送通知——从闭源的 Play Services 全家桶里解耦出来。预装 GMS 的设备上，Play Services 在后台常驻一整套遥测、广告、分析、定位等活动；microG 只做应用真正需要的那几项服务：云消息推送、设备注册、基础的 API 模拟，不收集用户数据、不跑静默分析。

它最适合两类用户：一类是刷了去谷歌化 ROM（如 /e/OS、LineageOS 非 GMS 版）的用户，设备上没有 Play Services 就装不上 WhatsApp、Telegram、Spotify 这类依赖推送的应用；另一类是有 root 权限想精简系统的玩家，用 microG 替换掉臃肿的 Play Services 来省电池、省内存。社区和 CalyxOS 等预装型系统的文档都把"更省电池、内存与 CPU"列为特性，这不是宣传口号——它跑起来之后，系统电池统计里你会看到 microG 的占比通常远低于 Play Services。

不是所有应用都能完美兼容。依赖 Play Integrity Device 档强校验的银行类应用、依赖谷歌地图完整 SDK 的导航应用，在 microG 下可能拒绝启动或部分功能缺失。这是框架的能力边界，不是 bug。

## 🔧 安装步骤

microG 的安装方式取决于你的设备基础——是已经刷好去谷歌化 ROM 还是在原系统上手动覆盖。前者预装型的系统在设置向导里会引导你一键启用，不需要额外操作；后者是本文的主要覆盖场景。

### 安装前核对

在动手之前，先确认三个前提：

1. **设备有 root 权限**：microG 要替换系统层面的服务，没有 root 装不上；如果是 LineageOS，需要同时刷 Magisk 或 SuperSU。
2. **系统里没有 Play Services**：如果 Play Services 还在，microG 会被抢占注册权，两者冲突必然崩溃。要么用 Magisk Hide 把 Play Services 模块停用，要么刷完 ROM 就没装 GMS。
3. **Android 版本 ≥ 8.0**：microG 对老版本 Android 的支持在近几年逐渐收窄，6.0/7.0 的设备建议找社区 fork 的旧版。

### 安装流程

1. **下载安装包**：从下载页拿到最新版本的 microG Services Core 安装包，同时下载 FakeStore（伪装应用商店的组件，解决部分应用检测不到 Play Store 的问题）。

2. **安装 FakeStore 先装**：FakeStore 是基础依赖，先安装它。如果应用安装器提示"签名不一致"，忽略继续——这是预期内的伪装行为。

3. **安装 microG Services Core**：装完 FakeStore 再装 Services Core，安装完成后**不要立刻打开**，先重启设备。

4. **首次启动向导**：重启后打开 microG，进入设置界面。你会看到四个主开关：云消息、设备注册、位置服务、地图服务。第一次全部打开也没问题，后面可以按需裁剪。

> [!TIP]
> 系统设置 → 电池 → 电池优化，把 microG Services Core 添加到**不受优化**列表。这条长连接被系统杀掉，推送消息就堵在半路了——这是新手最常犯的错误，排查耗电和消息问题时第一个确认它。

5. **过自检**：microG 设置里有个"自检"入口，跑一遍确保所有项都打绿勾。如果有红色叉号——常见的是"签名伪装失效"——先按提示修复再往下走，不然设备验证等功能会连带失败。

### 版本核对

装完后在 microG 设置 → 关于里查看版本号，与下载页标注的最新稳定版比对。开发版（nightly）可能有已知的后台缺陷，遇到耗电异常先排查版本是否稳定。

## 📖 使用入门

microG 装完不会让你立刻感受到变化——它是一个静默运行的后台框架，体验改善体现在应用层面。下面分几个高频场景说透它是怎么工作的，以及遇到问题时从哪入手排查。

### 推送通知是怎么接管的

安卓上聊天、邮件、资讯类应用的消息到达，绝大多数依赖谷歌的云消息服务（FCM，旧称 GCM）。应用自己并不维护到消息服务器的连接，而是把这事托付给系统里的谷歌框架——没有 GMS 的设备上，这个角色就由 microG 接管。

完整链路分四步：

1. **应用注册**：应用第一次启动时向推送系统注册，拿到属于自己的令牌。这一步由 microG 代为完成，前提是云消息开关已打开。
2. **设备注册**：microG 每天在后台向谷歌登记一次设备，这是推送等多项服务的前置身份。
3. **长连接待命**：开关打开后，microG 与推送服务器维持一条持久连接。
4. **消息分发**：服务器有新消息时经由这条连接送达 microG，再由它转交给对应应用弹通知。

这是一条 TCP 长连接，空闲时几乎静默——大部分时间它只是在等服务器说话，偶尔心跳保活。相比官方 Play Services 附带的分析、遥测、广告等全套后台活动，这条连接的开销通常小得多。

> [!NOTE]
> 为什么一条长连接比各家自己轮询省电？没有统一推送的设备上，每个聊天应用都得自己保活轮询，十几个应用就有十几条后台心跳。microG 把它们合并成**一条**系统级长连接：一条连接伺候所有应用，屏幕灭了也能收消息，代价远小于 N 个应用各自为战。

### 推送耗电异常时查哪

"装了 microG 之后耗电变快"的体感大多不是框架本身的问题。先去系统设置 → 电池 → 用电量排行，看耗电榜首是谁：

| 场景 | 结论 | 下一步 |
| --- | --- | --- |
| microG 本身占比高 | 框架侧有问题 | 查下面三个自查点 |
| 其他应用占比高 | 锅在应用 | 对比之前没推送时的耗电，框架只是让应用"活"得更正常了 |

框架侧三个自查点按优先级排查：

1. **连接在反复重连吗**：弱网环境下长连接频繁断开重连是耗电尖峰的经典来源——重连握手比维持连接费电得多。地铁、电梯里的耗电异常多属此类，换个网络环境对比耗电速率即可验证。
2. **电池优化豁免丢了吗**：系统更新可能重置豁免设置，被优化后的反复唤醒反而更费电。回设置确认豁免状态。
3. **版本有没有已知问题**：个别版本出现过后台相关的缺陷报告，升级最新稳定版试试。

> [!WARNING]
> 刚装完的头一两天，各应用集中重新注册推送、补同步数据，耗电偏高是正常波动，第三天再看趋势才有意义。别因为第一天的电量数据就急着卸载或重装。

如果排查无果，可以做一个极端重置测试：关掉云消息与设备注册两开关 → 重启 → 观察一天。耗电恢复正常即问题锁定在推送链路；再逐个打开开关、逐段观察，定位到具体环节。

### 设备验证（Play Integrity 基础档）怎么过

部分应用（尤其是金融类、游戏类）启动时会调用 Play Integrity API 校验设备完整性。microG 环境下通常只能通过**基础档**（MEETS_BASIC_INTEGRITY），Device 档和 Strong 档会红叉——这是预期结果，不必纠结红叉，只要基础档打绿勾就行。

过基础档的前置条件：

1. **设备证明开关打开**：microG 设置里与设备验证相关的开关保持开启，它控制 microG 是否响应应用的校验请求。
2. **自检全勾**：签名伪装失效的环境，校验大概率连带失败，先过完自检。
3. **部分场景需要登录谷歌账号**：社区经验中，个别校验路径在有谷歌账号在场时更顺利——预装型系统（如 /e/OS）的官方文档就把"系统级登录谷歌账号"列为通过基础校验的步骤之一。先不登录试一次，不行再补登录。

跑验证的流程很简单：安装一个验证检测应用（Play Integrity API Checker 或 YASNAC），点击检查按钮，观察结果。

> [!NOTE]
> 基础档通过 ≠ 所有银行应用可用。应用各自决定采信哪一档，采信 Device 档的应用照样拒绝。microG 能做到的上限就是基础档，Device 档需要完整的硬件安全模块背书，开源兼容层模拟不了。

校验不过时，按以下顺序排查：先排除 root 设备本身更难过检的因素 → 确认 microG 版本（DroidGuard 相关实现随版本持续修复） → 等一等再试（校验结果有缓存，刚改完配置立刻重测可能拿到旧结果）。

### 按需裁剪：不用推送的场景

如果你的设备只当离线工具、完全不需要消息推送，可以在 microG 设置里同时关掉云消息与设备注册两开关，microG 对谷歌的常驻连接随之消失——这是隐私最大化路线，代价是各类应用消息不可达。裁剪选项整理如下：

| 需求 | 做法 | 代价 |
| --- | --- | --- |
| 不要推送，其余照常 | 关云消息，保留设备注册 | 应用消息不可达 |
| 隐私最大化 | 两个开关都关 | 推送、登录均不可用 |
| 正常用推送 | 保持默认全开 | 常驻一条连接 |

连接是共享的，装十个聊天应用和装一个，microG 维持的连接数一样。真正影响耗电的是各应用自己的后台行为——那部分与 microG 无关，判断耗电来源时别把应用的锅扣给框架。
