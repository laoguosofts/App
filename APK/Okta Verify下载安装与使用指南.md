## ✨ Okta Verify 是什么：企业级多因素认证的移动端

Okta Verify 是 Okta 提供的企业级多因素认证（MFA）移动应用，用于在登录公司系统时完成身份的二次确认。它不是独立的账户管理器，而是挂靠在组织的 Okta 身份平台之下——组织管理员预先配置好认证策略和注册方式，员工拿到应用后完成登记，日常登录就靠它。

它支持三种核心验证方式：推送通知批准、六位动态码输入，以及 FastPass 免密码通行（设备内公私钥对做加密应答）。部分组织还会开启号码匹配、生物识别确认等附加安全策略。与市面上的通用认证器（如 Google Authenticator）相比，Okta Verify 更贴合企业场景——账户由管理员统一管理、策略可集中下发、还能接入组织的风险评分引擎。

适用人群就是企业员工、学校师生和任何接入了 Okta 身份平台的组织成员。如果你所在的公司登录系统时会跳出「Okta Verify」的验证环节，那这款应用就是为你准备的。

## 🔧 安装步骤：版本核对与权限准备

### Android 平台

1. **版本核对**：安装前先确认手机系统版本在官方支持清单之内。较新的 Okta Verify 要求 Android 8.0 以上，旧系统可能无法通过组织注册。
2. **下载来源**：优先走 Google Play，或使用上方下载入口获取 APK 文件。如果使用 APK 侧载，需要在系统设置里允许「未知来源」安装——安装完成后建议把这个开关关掉，保持其他来源的默认禁用。
3. **权限授予**：首次启动时应用会依次申请通知、摄像头、蓝牙等权限。摄像头用于扫码注册，蓝牙用于换机场景下的账户迁移，通知权限必须全部开启（包括锁屏通知），否则推送验证无法到达。
4. **锁屏前置**：组织若开启了「必须确认」类策略，应用会引导你去系统设置里设置锁屏密码或生物识别——这一步是注册的前置条件，跳过不了。

### iOS 平台

从 App Store 直接安装即可，权限请求的顺序和 Android 类似。iOS 的推送通道由 APNs 负责，通常不会出现 Android 端常见的端口拦截问题，但勿扰/专注模式仍然可能吞掉通知。

> [!TIP]
> 安装后别急着打开应用乱点。不少人误把自己注册到了错误的组织地址下，后续要么删账户重来、要么找管理员清理。先看清登录页面上写的是哪个组织，再动手注册。

## 📖 使用入门：从注册到日常验证的完整路径

### 注册前花两分钟核对三件事

注册本质是「把你的设备登记进组织的准入名单」，它同时受三方面条件约束：

1. **组织地址**：就是你们公司登录系统的网址（形如 `公司名.okta.com` 或公司自己的域名）。它通常出现在 IT 发的入职邮件里、登录系统时浏览器地址栏，也可以直接向 IT 帮助台询问。扫码注册虽然不手输地址，但出问题时核对地址能排掉一大类错误（注册错了组织）。

2. **管理员开放了哪些注册方式**：常见的有四条路，不是每家组织都全开：

| 注册方式 | 适用场景 |
| --- | --- |
| 浏览器扫码 | 最常见的默认路径，电脑登录页显示二维码，手机扫 |
| 应用内直连 | 安全要求高的组织，在应用里输入组织地址完成注册，也是 FastPass 同设备注册的基础 |
| 激活链接 / 密钥 | 短信或邮件里的链接，或手动输入一串密钥，摄像头不便或扫码失败时用 |
| 蓝牙设备间迁移 | 换机场景，旧设备导出、新设备导入 |

如果登录页面提示的选项和同事描述的不一样，多半是组织策略差异，别硬套别人的步骤。

3. **设备本身达标**：系统版本在支持范围内、摄像头可用且能对焦、组织要求高安全时设备已设好锁屏密码或生物识别。

### 日常验证的三种方式

注册完成后，日常登录时系统会让你选验证方式，三种方式在体验和安全上各有侧重：

**推送通知批准**：最省心的方式。登录页点一下「发送推送」，手机弹出通知，点开确认后登录完成。但推送依赖网络通道——如果公司 Wi-Fi 下永远收不到，大概率是防火墙拦了谷歌推送服务的端口（5228、5229、5230），需要找 IT 放行。切到手机流量立刻恢复的，基本可以确定是这个原因。

> [!WARNING]
> 推送请求五分钟不处理就过期。别盯着一个旧请求傻等，也别连点七八次生成一堆多余请求互相覆盖。正确姿势是回登录页重新选一次推送，一次只等一条。

**六位动态码**：推送收不到或网络不稳定时的兜底方案。应用内打开就能看到一串每 30 秒刷新的数字，手动输入到登录页即可。动态码不依赖网络，脱网也能用，适合出差、弱网环境。

**FastPass 免密码通行**：如果组织开通了 FastPass，登录页会出现一个独立的「Sign in with Okta FastPass」按钮，点一下就能过——连密码都不用输。它是设备内生成的公私钥对做加密应答，私钥不出设备，同时校验请求来源。钓鱼网站冒充登录页时，FastPass 的来源校验对不上，验证直接失败，这一点是动态码和推送都做不到的。

FastPass 的触发形态由设备状态和组织策略共同决定，可能是静默通过（点按钮即过，无感）、生物识别确认（扫指纹或面容）、或口令确认（输设备锁屏密码）。需要注意两个已知的浏览器坑：无痕模式下 FastPass 不会被拉起，退出无痕再试；Firefox 和三星浏览器可能提示需要额外设置，此时改用动态码或推送即可。

### 号码匹配：推送里的安全附加层

如果你批准推送时多了一步「从列表里选出登录页显示的数字」，那是组织开启了号码匹配。这个看似多余的步骤堵的是推送验证的一个真实漏洞——早期推送验证存在「推送轰炸疲劳」攻击：攻击者反复触发登录请求，受害者手机被一连串推送轰炸，不少人手滑点了批准。号码匹配把「闭眼点同意」变成了「必须看着登录页上的数字来选」，手机不在攻击者面前、看不到那个数字，瞎选是过不了的。

开启后的流程是：登录页显示一个两三位数字，手机推送点开后同样进入数字选择界面，选出与登录页一致的数字才能批准生效。有两个实用提醒：

- 组织已开启号码匹配时，一条不要求选数字的「批准」请求本身就可疑——正常流程必须有数字环节；
- Apple Watch 端批准同样要过号码匹配这一关，流程一致。

### 推送收不到的三层排查

推送丢失的原因几乎都落在三层，按顺序排查，两分钟内能定位绝大多数情况：

| 层级 | 排查要点 |
| --- | --- |
| 手机通知权限 | 系统设置 → 通知 → 确认允许通知开着（锁屏通知也建议开），勿扰/专注模式没有吞掉这条通知 |
| 推送通道网络环境 | 公司 Wi-Fi 下永远收不到 → 防火墙拦了推送端口；切流量正常 → 公司网络拦截实锤；所有网络都收不到 → 通道长连接断开，开关一次飞行模式或重启手机 |
| 请求是否已过期 | 推送请求五分钟不处理就过期，回登录页重新选一次推送生成新请求 |

排查后仍收不到的，确认账户详情页里推送方式是开通状态，跑一遍应用内置排障器，实在不行改用动态码顶住当天工作，然后找 IT——网络类原因必须管理员侧解决。
