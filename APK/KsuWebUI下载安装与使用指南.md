## ✨ KsuWebUI 是什么

KsuWebUI 是一套运行在手机浏览器里的 Root 管理界面——它把 KernelSU、Magisk、APatch 这些底层 Root 框架的常用功能统一打包到一个网页里，不需要单独安装 APP，直接在手机浏览器打开就能用。

对已经刷好 Root 框架的用户来说，KsuWebUI 解决的痛点很实际：不同框架有各自的管理器 APP，界面风格、操作路径都不一样；换手机、换框架就要重新适应一遍。KsuWebUI 用浏览器作为唯一载体，底层框架无关，装一次就能覆盖 KernelSU、Magisk、APatch 三种主流 Root 方案。

核心能力大致分成四块：模块管理（安装、启停、查看版本和详情）、Root 权限管理（看哪些 APP 拿了权限、什么时候用的）、日志排查（模块运行日志、Root 操作审计）、排错工具（模块冲突定位、安全模式辅助）。适合有一定折腾经验、喜欢刷模块做定制的 Android 用户，也适合刚入门 Root、想找一套统一界面来管理框架的新手。

## 🔧 安装步骤

KsuWebUI 的安装方式和普通 APK 不同——它本质上是一个本地运行的网页服务，需要在已经有 Root 框架的 Android 手机上部署。

### 安装前的准备

在开始之前，先确认两件事：

1. **手机已刷好 Root 框架**（KernelSU、Magisk 或 APatch 任一即可），并且框架管理器能正常工作
2. **手机浏览器开启了「允许本地文件访问」**——大多数浏览器默认关闭这个选项，需要在设置里手动打开

### 部署方式

按下载页的说明操作，核心流程是：

1. 从下载页获取最新版本的 KsuWebUI 网页包（通常是一个 ZIP 文件）
2. 把 ZIP 解压后得到的文件放到手机的 `/data/adb/ksu/` 目录（KernelSU）或对应的框架目录下
3. 给文件设置正确的权限（参考下载页给出的 chmod 命令）
4. 在框架管理器中启用 WebUI 功能，或者直接用浏览器访问本地地址

> [!WARNING]
> 安装路径和权限设置是最容易出错的环节——路径不对会导致浏览器打开后一片空白，权限不对则会报「无法读取框架数据」。建议严格照下载页给的命令逐条执行，不要自行修改路径。

### 核对是否安装成功

部署完成后，在手机浏览器打开 KsuWebUI 的本地地址，如果能看到模块列表、权限管理、日志排查这些导航项，并且数据能正常加载，就说明部署成功了。如果浏览器提示「无法连接到服务器」，回头检查一下框架管理器里的 WebUI 开关是否已经打开。

## 📖 使用入门

KsuWebUI 的侧边栏导航把所有功能分组得很清楚，首次进入大致按「模块管理 → 权限检查 → 日志熟悉 → 排错准备」这个顺序走一遍，后面日常使用就会很顺手。

### 模块管理：装、停、看版本

模块管理是 KsuWebUI 最核心的功能。每个已安装的模块都显示在列表里，点击任意一条进入详情页，可以看到：

| 信息项 | 说明 |
|--------|------|
| 模块名称和版本号 | 模块的友好名称 + 当前安装版本 |
| 作者和描述 | 模块开发者 + 功能简介 |
| 安装路径 | 模块文件实际存放在哪里（KernelSU 是 `/data/adb/ksu/modules/`，Magisk 是 `/data/adb/modules/`，APatch 是 `/data/adb/ap/modules/`） |
| 运行状态 | 当前启用/禁用、最后启动时间、后台服务是否正常 |

> [!TIP]
> 模块详情页里的安装路径很有用——如果需要手动查看或修改模块文件（比如改配置文件、手动禁用模块），可以记下这个路径，然后用 Root 文件管理器进去操作。

更新模块不需要先卸载旧版本：从下载渠道拿到新的 ZIP 包后，用和安装时相同的方式覆盖部署，模块安装脚本会自动替换旧文件，重启生效。

### Root 权限管理：谁在悄悄用你的最高权限

Root 权限是 Android 上的最高权限——拿到 Root 的 APP 可以读写任何文件、执行任何 shell 命令。KsuWebUI 的「Root 权限」分组里有一个授权应用列表，每个条目显示：APP 图标和包名、授权时间、授权模式（永久允许 / 仅本次 / 拒绝）、最近一次使用 Root 的时间。

默认按最近使用时间排序，最上面的就是刚刚用了 Root 的 APP。定期扫一眼这个列表，看看有没有不该拿 Root 的 APP 混进来——比如一个普通的社交 APP 或者游戏，如果它出现在授权列表里，就值得警惕。

典型需要 Root 的 APP 大致分这几类：框架管理器本身（KernelSU、Magisk Manager）、Root 文件管理器（Root Explorer、Solid Explorer）、系统工具（终端模拟器、CPU 调节工具）、备份恢复（Titanium Backup）、广告拦截的 Root 模式。不在这个范围里的 APP，如果请求 Root 权限，大概率可以拒绝。

### Root 操作审计：所有 shell 命令都记录在案

KsuWebUI 有一个很容易被忽略但很实用的功能：操作审计日志。它会记录每一次通过 su 发起的 shell 命令——哪个 APP 请求的、执行了什么命令、什么时候执行的、结果如何、退出码是多少。

审计日志和模块日志是两回事：模块日志是模块脚本自己 echo 出来的输出，审计日志是框架层面对所有 su 调用的统一记录，粒度更细、覆盖更广。比如：

- `su -c "rm -rf /data/app/xxx"` → 删除了某个 APP 的数据
- `su -c "mount -o remount,rw /system"` → 重挂载了 system 分区为可写
- `su -c "chmod 777 /etc/passwd"` → 修改了系统文件权限

这些操作在审计日志里一条都跑不掉。安全敏感场景下可以用它排查可疑操作，日常排错时也能用来追踪「谁在什么时候执行了什么命令导致系统出问题」。

> [!NOTE]
> 审计日志不会记录内核态的操作（比如 KPM 模块在内核里做的事），也不会记录 Magic Mount 直接替换 system 分区文件的操作——那些操作不产生独立的 su 调用。

审计日志默认开启，会持续累积。存储占用不大，建议保持启用，定期清理或导出 JSON/CSV 备份即可。关闭后虽然能省一点存储空间，但也失去了安全追踪能力。

### 模块冲突排查：从轻到重的四步法

装了新模块后如果出现 APP 闪退、手机卡顿、发热异常，甚至开机循环这些症状，大概率是模块冲突。KsuWebUI 自身提供了排查工具，加上一些 Recovery 层面的兜底手段，可以从轻到重逐步定位：

**第一步：回想最近装了什么。** 症状出现前最后装的那个模块嫌疑最大，先在 KsuWebUI 里禁用它观察一下。

**第二步：二分法缩小范围。** 如果不知道哪个模块出问题，就先禁用一半模块（保留框架本身和基础类模块），重启观察——正常则问题在刚才禁用的那一半里，不正常则在保留的那一半里。在嫌疑组里重复这个过程，3~4 轮就能定位到具体模块。

**第三步：看依赖关系。** 问题模块可能依赖另一个模块，依赖模块本身有问题、版本不匹配，或者两个模块同时 hook 同一个 APP 导致冲突，都是常见原因。

**第四步：查日志确认。** 在 KsuWebUI 的日志页面看目标模块有没有 `[ERROR]` 级别的报错，`[WARN]` 级别的是兼容性警告，没日志说明模块根本没运行起来。

> [!WARNING]
> 如果模块导致手机无法正常开机，先用安全模式救场：开机时按住音量键（不同机型按键不同）进入安全模式，第三方模块不会加载。安全模式能进就说明确实是模块的问题。如果有 TWRP Recovery，可以直接进 Recovery 找到 `/data/adb/modules/` 目录，给嫌疑模块的目录名加 `disable_` 前缀让框架跳过加载，重启就能进系统了。

养成几个习惯能大幅降低冲突概率：一次只装一个新模块、装完观察几天再装下一个；看模块评论区有没有人反馈兼容性问题；优先选更新活跃的模块；旧版本模块及时更新；不用的模块定期清理。模块越多互相冲突的概率越高，保持精简是最直接的防冲突手段。
