## ✨ App Ops：让 Android 权限真正为你所用的神器

App Ops 是一款专注于 Android 应用权限精细控制的工具。它操作的不是系统设置里那些运行时权限开关，而是 Android 内部隐藏的 **appops（Application Operations）服务**——这是一套比运行时权限更底层、更细腻的权限控制机制。

Android 系统早在 4.3 版本就引入了 appops 服务，但谷歌从未在系统设置里开放用户可配置的界面。App Ops 的存在价值就在于：通过 Shizuku 或托管设备管理员权限，让普通用户也能直接操作这套隐藏的权限系统。

App Ops 能做什么？核心能力集中在几个方面：

- **精细到"忽略"级别的权限控制**：把某个权限设为"忽略"后，应用不会收到错误，但只会收到空白数据。比如让相机权限忽略，应用以为自己拿到了相机但实际拍不到东西。
- **批量模板应用**：手动调好一个应用的权限后存为模板，一键套用到一组同类应用。
- **后台行为独立控制**：Android 9 引入的 `RUN_ANY_IN_BACKGROUND` 和 `RUN_IN_BACKGROUND` 两个后台权限可以分别设置，不再一刀切。
- **系统追踪权限的可视化**：appops 会记录每个应用的权限使用行为，App Ops 可以把这些追踪信息展示出来。

它适合谁？任何想对手机应用"拿回控制权"的人——厌倦了每装一个 App 就被索取一堆无关权限、讨厌后台偷跑耗电、想统一管理几十个应用权限的老用户。

## 🔧 安装与激活：两种模式的选择

App Ops 本身只是一个界面层，真正的能力来自两种激活模式。安装完成后，选择哪种模式取决于你的需求和系统版本。

### 第一步：安装基础组件

1. 安装 App Ops 主应用
2. 安装并打开 Shizuku（推荐）或 Island（DPM 模式可选）
3. 授予应用所需的基础权限

### Shizuku 模式：最推荐的路径

Shizuku 通过 ADB 桥接获得 shell 级权限，是目前功能最完整的激活方式。

**激活步骤**：

1. 手机开启 USB 调试，连接电脑
2. 电脑执行：
   ```
   adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh
   ```
3. 或通过无线调试方式，在手机端直接运行上述命令
4. Shizuku 服务启动后，App Ops 自动获取权限

> [!WARNING]
> Shizuku 模式的局限在于**每次手机重启都需要重新激活**。如果嫌麻烦，可以考虑 DPM 托管模式作为备选。

### DPM 托管设备管理员模式：一次设置长期有效

托管设备管理员模式（Delegated Device Admin）让 App Ops 成为系统特权应用，重启后仍然生效。适合不想每次重启都重新 ADB 激活的用户。

**设置前置条件**：需要安装一个支持 Delegated Scopes Manager 的管理员应用（如 Island v5.0+）。

**设置步骤**：

1. 安装 Island 并将其设为设备管理员
2. App Ops 设置 → 选择"托管设备管理员模式"
3. 系统弹出设备管理员授权对话框，勾选"修改 app ops"
4. ADB 执行额外命令授予读取权限：
   ```
   adb shell pm grant --user 0 rikka.appops android.permission.GET_APP_OPS_STATS
   ```

### 两种模式对比

| 对比项 | Shizuku 模式 | DPM 托管模式 |
|-------|-------------|-------------|
| 激活方式 | ADB 启动服务，重启需重激活 | 一次性设置，长期有效 |
| appops 能力 | 完整 | 完整 |
| Android 11"每次都询问" | ✅ 支持 | ❌ 不支持 |
| permission flags | 可读写 | 无法设置 |
| 额外依赖 | Shizuku 应用 | Island 或其他 DPM 管理员 |

> [!TIP]
> 如果你追求完整功能、Android 11+ 系统需要"每次都询问"权限状态——选 Shizuku。如果嫌重启激活麻烦、且不需要 permission flags 功能——DPM 模式也能满足大部分场景。

## 📖 核心功能与使用进阶

### 理解 appops：为什么系统里找不到这个开关

Android 系统的权限体系分为两层。第一层是你在系统设置里看到的运行时权限（相机、麦克风、定位等），安装和运行时会弹窗让你选择。第二层就是 appops——一套隐藏的"应用操作"追踪和控制服务。

appops 与运行时权限的关系：应用尝试执行某个操作时，系统**先检查运行时权限是否授予，再检查对应的 appops 设置**。运行时权限没授予 → 应用收到报错。运行时权限已授予但 appops 被设为"忽略" → 应用**不会报错，但只会收到空白数据**。这就是 App Ops 的核心价值所在——比单纯拒绝权限更巧妙地拦截。

部分 appops 与系统权限**对应**（如 `OP_CAMERA` 对应相机权限），其余则对应**系统根本没有开放控制的功能**（如 `OP_READ_CLIPBOARD` 读取剪贴板——你在系统设置里找不到"剪贴板权限"的开关，但 App Ops 能控制）。

> [!NOTE]
> 每个 appop 在系统中有两种 mode：package mode（针对应用包名）和 uid mode（针对用户 ID）。uid mode 优先级更高，只有它为默认值时才会使用 package mode。理解这个优先级能帮你排查"为什么我改了权限但没生效"。

### 后台运行权限：Android 9 的两道闸门

Android 7 引入了 `RUN_IN_BACKGROUND` appop，控制应用进程在后台能否继续执行代码。Android 9 又新增了 `RUN_ANY_IN_BACKGROUND`，比前者更严格——禁止的是"在后台启动任何类型的服务"这个行为本身。

App Ops 在 v2.6.0 之前把两者视为同一个"在后台运行"选项，修改时同时改动两个 appop。v2.6.0 起改为**可以独立选择限制哪一个**，因为某些场景下同时限制会过于激进。

### 四种后台限制策略

| 方案 | RUN_IN_BACKGROUND | RUN_ANY_IN_BACKGROUND | 适用场景 |
|------|-------------------|----------------------|---------|
| 最激进 | 忽略 | 忽略 | 游戏、娱乐类，完全不想让它后台运行 |
| 平衡推荐 | 允许 | 忽略 | 想限制后台耗电但不想完全断推送 |
| 温和 | 忽略 | 允许 | 限制后台代码但保留后台服务能力 |
| 完全开放 | 允许 | 允许 | 依赖后台服务的应用（音乐、下载器、VPN） |

> [!WARNING]
> 厂商定制 ROM（MIUI、ColorOS、OneUI）通常有自己额外的激进后台管理机制。App Ops 的设置可能与厂商策略叠加或被覆盖，某些厂商甚至会在系统层面强制把某些 app 设为 `RUN_ANY_IN_BACKGROUND = ignore`，App Ops 也改不了。

### 批量权限修改：告别逐个点来点去

装了几十个应用后，逐个进入 App Ops 改权限是重复劳动。批量操作适合几种典型场景：**同类型应用统一策略**（所有新闻 App 忽略定位、所有购物 App 忽略剪贴板）、**新手机初始化**（迁移数据后批量套用习惯设置）、**APP 大版本更新后复查**（新版本可能新增了权限请求）。

**模板批量应用是最推荐的路径**：

1. 手动进入某个应用的详情页，逐个调好权限，确认效果正确
2. 在权限设置页选择"保存为模板"
3. 回到应用列表，多选目标应用，选择"应用模板"
4. 模板会覆盖目标应用的现有 appops 设置

模板方式的优势在于"先验证再批量"——你自己确认过效果正确才会大规模应用，风险可控。

**按权限项反查**也是常用技巧：想知道"手机上哪些应用索要了麦克风权限"，进入 App Ops 设置 → 行为 → 全部权限 → 找到麦克风对应的 appop → 查看哪些应用声明了这个权限 → 逐个设置。

**刷机恢复**则是最快的批量应用方式：安装 App Ops + Shizuku + 激活 → 从之前的备份文件恢复所有设置，一次把过去所有手动设置全部还原。

> [!WARNING]
> 批量操作**不可逆**，会覆盖目标应用的现有设置。大规模批量修改前务必先导出当前备份。系统应用不要批量改，除非你非常确定自己在做什么。批量应用后用 App Ops 的"已修改"筛选快速验证，Android 11+ 系统可能会把部分设置自动重置，恢复后过一段时间再检查一次。
