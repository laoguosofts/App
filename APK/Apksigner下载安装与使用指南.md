## ✨ Apksigner 是什么

Apksigner 是一款运行在 Android 手机上的 APK 签名与验真工具。它的核心定位很清晰：把原本需要 Android SDK 命令行才能完成的签名操作，搬到了手机界面上，让没有 PC 环境的用户也能给 APK 重签、验真。除此之外，它还内置了一套知名品牌签名库，可以一键识别下载来的 APK 是否被换壳重打包过。

对于需要自己管理 APK 签名的用户来说，Apksigner 的价值不只是一个界面化的签名器——它还能导出 jar 文件到电脑、统一手机端与 PC 端的签名口径、在签名冲突时快速定位原因。

## 🔧 安装步骤

Apksigner 是 Android 独占应用，不需要 PC 安装包。安装过程本质上就是把 APK 装进手机，但首次安装前有两点要提前做对。

### 准备工作：开启未知来源安装

手机系统默认禁止从应用商店之外的来源安装 APK。从官方下载页拿到 APK 后，系统会弹出「未知来源安装被阻止」的提示。此时需要进系统设置：

1. 打开手机的**设置 → 安全 → 安装未知应用**（不同手机品牌路径略有差异，小米、华为、OPPO 的入口名称可能不同，搜「未知来源」关键字能直接定位）
2. 找到你用来下载 APK 的那个浏览器（或文件管理器），把它的「允许安装未知应用」开关打开
3. 回到 APK 文件点击安装，按屏幕提示完成

> [!WARNING]
> 未知来源开关不要给所有应用都开，只给你确定可信的下载工具开。用完可以关掉，避免其他应用偷偷装包。

### 版本核对：装完确认是对的那份

首次安装成功后，打开应用进「关于」标签页，核对版本号与官方下载页标注的是否一致。如果版本号对不上，说明装的不是最新版，建议卸载后重新下载。

## 📖 使用入门

打开应用默认落在「签名」标签页，页面中央显示「没有文件」，右下角有一个扳手形状的悬浮按钮——这是所有签名操作的起点。界面整体是深底浅字的默认深色主题，标签页依次为签名 / 应用程序 / 验证 / 秘钥库 / 关于，应用语言跟随系统，简体中文系统直接显示中文标签。

### 首次启动的关键设置

第一次实际操作时应用会先后请求两类系统权限，建议当场授予：

- **存储 / 文件访问**：读取要签名的 APK、读写输出目录都靠它。拒绝了它，签名文件时会停在选文件这一步
- **安装应用**（可选）：如果打算用抽屉菜单直接安装 apk 或 split-apks，需要放行「安装未知应用」授权

> [!TIP]
> 建议先别急着签名，先进「秘钥库」标签页确认有没有可用的密钥。密钥就位之前，签名流程走不动——这好比没有私钥就没法盖章。

### 日常签名流程的核心逻辑

签名操作的基本流程很直观：选文件 → 选密钥 → 签 → 输出。但有几个容易踩坑的地方值得提前留意。

**密钥与签名的关系**：每把密钥对应一套签名证书。用同一把密钥签出来的 APK，系统才认为是同一个应用的升级包。如果换了密钥签，哪怕是同一个应用，覆盖安装也会报签名冲突。

**输出文件的命名管理**：签名完成后输出的 APK，建议在文件名里带上版本号和签名日期，比如 `myapp-v2.3-signed-20261018.apk`。这样一段时间之后回头找，不会搞混哪份是哪次签的。

### 验真功能：识破换壳重打包

Apksigner 的验证功能是它区别于普通签名器的核心能力。重打包的完整链条是：拿到原厂 APK → 反编译改动 → 重新打包 → 必须重新签名（原厂私钥不在攻击者手里）→ 分发。链条上任何一步都能做到以假乱真，唯独签名这步做不到「和原厂一样」——它要么是原厂签名（没动过），要么是别的签名（动过）。

应用内置了一份知名品牌的签名名单，验证时自动比对：

- 对手机里**已安装**的应用：直接在「应用程序」标签页选择已装应用进行验证
- 对**下载未装**的 APK：在「验证」标签页选文件验证

两条动线都会给出比对结果——签名是否匹配某个已知品牌。典型的识破场景包括：第三方小站流传的「大厂应用」显示签名对不上该品牌（仿冒实锤），群里流传的「更新版」签名是陌生证书（典型的重签重打包），来路不明的「内测版」签名既不是原厂也不是任何已知品牌（来源可疑，删除处理）。

> [!NOTE]
> 品牌名单的覆盖范围随应用版本迭代可能增补，不在名单内的小众应用验不出「品牌归属」，这种情况退回签名有效性判断即可——签名本身是否有效、证书是否过期，这些基础验证不受名单限制。

### 导出 jar 到电脑：签名能力的跨平台延伸

侧边抽屉里有一个「导出 apk-signer.jar」的选项，把签名器的 jar 形态导出到存储，供电脑上的 Java 运行环境使用。等于把手机上这套签名能力复制一份到 PC 命令行里，适合三种场景：

- **批量签名**：电脑上存着一堆包要处理，逐个传到手机签效率太低，电脑端直接批量跑
- **接入脚本**：打包流程已经脚本化的用户，把签名命令嵌进构建脚本
- **电脑环境受限**：不想装完整的 Android SDK，只要一个能跑的签名器

使用前提很简单：电脑上有 Java 运行环境，密钥库文件也在电脑上可访问的位置。导出的 jar 附带使用说明，命令行参数可能随版本变化，以导出时的说明为准。

> [!TIP]
> 手机端与电脑端建议用同一把密钥签名，输出口径统一。如果同一应用在两端签出两套不同的签名，会直接制造签名冲突，覆盖安装时系统报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

### 签名冲突自救动线

当你在网上找到一个常用应用的更新包（或自己重签过一份），覆盖安装时系统报签名冲突，可以按三步走通自救：

**第 1 步：定因（2 分钟）**——用验证功能分别验证手机里已装的旧应用和要装的新包，两边结果一对，结论三选一：新包签名与知名品牌一致、旧包也是（正主升级，冲突另有原因）；两边签名不一致（换签包，走重装动线）；新包签名无效（包有问题，重下）。

**第 2 步：数据决策（2 分钟）**——按「换签名覆盖安装的正确姿势」过一遍决策点：数据能不能丢、有没有应用内备份。

**第 3 步：卸旧装新（5 分钟）**——备份完成 → 卸载旧应用 → 用抽屉菜单安装入口装新包 → 打开应用确认数据迁移到位。

冲突解决之后，建议做一件事固化成果：如果根源是渠道来源混乱，以后固定从一个渠道拿这个应用的包；如果是自己重签导致的，把这次用的密钥与输出命名规则记下来，避免下次在同一应用上再出同样的问题。
